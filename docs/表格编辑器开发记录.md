## 一、起因

需求说起来很简单：在没装 Office 的机器上，能快速打开、查看、修改 `.xlsx` 和 HTML 表格，改完直接保存，不要安装、不要联网、不要一堆配置文件。

但它同时带着几个硬约束：

- 交付物必须是**一个可以直接双击运行的文件**；
- 要能在 **Windows 7 SP1 到 Windows 11** 上跑；
- 双击 `.xlsx` / `.html` 文件时，要用这个程序打开；
- 界面全中文。

最后做出来的是一个约 124MB 的通用单文件 exe，以及一个 11.7MB 的 Win10+ 轻量版。这篇文章记录技术选型、架构和踩过的坑。

## 二、最终交付

| 文件 | 体积 | 适用系统 |
| --- | --- | --- |
| `表格编辑器-Win7全版本.exe` | 129,854,270 字节（约 124MB） | Win7 SP1 – Win11，内置 WebView2 109 内核 |
| `表格编辑器-Win10轻量版.exe` | 11,762,868 字节（约 11.2MB） | Win10/11，依赖系统已装 WebView2 |

功能范围刻意保持克制：打开 xlsx（读第一张工作表）和 HTML 表格，多文件标签页，搜索、排序、批量修改、删除重复行、撤销重做、导出 Excel、保存前自动备份、最近打开历史、深色与自定义主题、拖放打开、单实例运行、文件关联管理；1.1.0 起加入公式与函数、WPS 风格按列筛选、冻结首行。

没有 PDF，没有 Word/PPT，没有 Markdown 预览。这些功能做过，后来全部砍掉——体积和启动速度是更重要的指标。

## 三、技术选型

### 后端：Python + 标准库

核心只有两个文件：

- `app.py`：窗口、HTTP 服务、单实例、文件关联、运行时内核管理；
- `sheetio.py`：表格读写、HTML 解析、备份。

没有用 Flask/FastAPI，直接用 `http.server.ThreadingHTTPServer`。进程内起一个只监听 `127.0.0.1` 随机端口的服务，前端就是普通网页，调试时用浏览器直接打开即可，不需要额外的开发服务器。

表格读写用 `openpyxl`，HTML 解析用标准库 `html.parser`。

### 前端：原生 HTML/CSS/JS

没有 React/Vue，没有构建步骤。前端最终作为静态资源打进 exe，构建流程越短，出问题的环节越少。界面用原生表格渲染，几万行数据靠分页式的可见区域渲染和列宽缓存保证流畅度。

### 窗口：pywebview + WebView2

选 pywebview 而不是 Electron/Tauri：

- Electron 一个空壳就 100MB 起步，和"轻量单文件"的目标冲突；
- Tauri 依赖系统 WebView2，在 Win7 上同样要处理运行时问题，而且 Rust 工具链的维护成本对这个项目不划算；
- pywebview 在 Windows 上就是 WebView2 的一层薄封装，Python 侧还能直接用 `ctypes` 调 Win32 API。

代价是 Win7 上没有 WebView2，必须自带运行时——这是后面最大的一块工作量。

## 四、架构

### 4.1 进程结构

```
表格编辑器.exe
├── Python 运行时（PyInstaller 解包）
├── HTTP 服务 127.0.0.1:<随机端口>
│   ├── 静态页面 /
│   └── /api/* 接口
├── WebView2 窗口（pywebview）
└── 数据目录 %LOCALAPPDATA%\表格编辑器\
    ├── 设置.json / 历史记录.json
    ├── 备份\ / 日志\
    └── WebView2\109.0.1518.140\（Win7 内置内核缓存）
```

所有数据都在本机，没有任何对外网络请求。

### 4.2 接口

接口数量不多，够用即可：

| 接口 | 作用 |
| --- | --- |
| `/api/open` | 打开文件并解析 |
| `/api/save` | 保存（保存前自动备份） |
| `/api/export` | 导出标准 Excel |
| `/api/history` | 最近打开记录 |
| `/api/settings` | 主题等设置 |
| `/api/dirty` | 未保存状态同步 |
| `/api/assoc` | 文件关联查询/建立/取消 |
| `/api/pending` | 取出待打开的文件队列 |
| `/api/open-request` | 接收另一个实例转交的文件 |

本地服务的接口用一次性随机 token 保护：启动时生成，写进 cookie（`SameSite=Strict`）和页面 URL，请求同时接受 header 和 query 形式。这样即使同一台机器上有别的网页，也无法随意调用本地接口。

### 4.3 单实例与文件转发

用户双击第二个文件时，不应该再开一个窗口，更不应该让两份程序同时写同一个文件。

实现分三层：

1. 命名互斥体 `Local\SheetEditor-...` 做进程级互斥；
2. 运行中的实例把端口、token、pid 写入 `运行实例.json`；
3. 新实例启动时读取该文件，向老实例 POST `/api/open-request`，把文件路径交过去，然后自己退出，并把老窗口切到前台。

前端每 1.2 秒轮询一次 `/api/pending`，拿到路径就打开成新标签页。用轮询而不是 WebSocket，是因为这个场景的实时性要求很低，轮询更简单也更稳。

## 五、踩坑记录

### 5.1 双击文件，程序毫无反应

这是用户反馈最直接的问题：某些文件已经设成用本程序打开，双击后什么都不发生。

排查后发现和关联无关，根因在入口参数：

```python
# 修复前
parser.add_argument("--port", type=int, default=0)
parser.add_argument("--debug", action="store_true")
# 没有位置参数
```

Windows 通过关联启动程序时，命令行是 `"表格编辑器.exe" "C:\...\文件.xlsx"`。`argparse` 遇到不认识的 `files` 参数会直接 `exit(2)`。而打包成窗口程序后没有控制台，错误信息无处可去，表现就是"双击没反应"。

修复很简单：

```python
parser.add_argument("files", nargs="*", help="要打开的文件")
```

再加一条完整链路：首实例把文件放进待打开队列；后续实例走 HTTP 转发。只修 argparse 是不够的——用户双击第二个文件时，还得让已经开着的窗口接住它。

### 5.2 Win10 的默认应用有哈希保护

文件关联写的是 `HKCU\Software\Classes`：

```
HKCU\Software\Classes
├── SheetEditor.TableFile
│   ├── shell\open\command = "<exe>" "%1"
│   └── DefaultIcon
├── Applications\表格编辑器.exe
│   └── SupportedTypes
└── .xlsx
    ├── (默认) = SheetEditor.TableFile
    └── OpenWithProgids
```

在 Win7/8 上这样写就够了。Win10/11 则多了一层 `Explorer\FileExts\.xlsx\UserChoice`，其中的 `Hash` 是根据用户选择计算的，程序无法伪造。也就是说，**Win10 之后无法用代码强行把某个扩展名的默认程序改成自己**。

处理方式不是硬碰，而是把选择权交回用户：

- 程序先把文件类型注册进"打开方式"列表；
- 界面检测到系统默认程序不是自己时，返回"需要确认"，并提供"系统默认应用"入口；
- 用户点一次确认即可。

关联前会把每个扩展名原来的默认值备份到 `关联备份.json`，取消关联时按备份还原；只有一个扩展名还指向本程序的 ProgID 时才删除 ProgID，避免误删别的程序正在用的键。

另一个必须提醒用户的事实：关联里记录的是 exe 的完整路径，**移动或重命名 exe 之后旧关联必然失效**，需要重新关联一次。这不是 bug，是注册表的工作方式。

### 5.3 Win7 上根本没有 WebView2

WebView2 的常青版运行时最低要求 Win10。Win7 最高只能用固定版本 109.0.1518.140，而且必须随程序分发。

最初的方案是把 314MB 的解压目录作为 PyInstaller 的 datas 打进去。结果很糟：onefile 每次启动都要解压全部文件，冷启动 11.4 秒，而且每次启动都多写 314MB。

最终方案是把运行时**追加在 exe 文件尾部**：

```
[PyInstaller 单文件 exe][tar.xz 运行时 121MB][24 字节尾针]
```

尾针用 `struct` 记录魔数、偏移和长度：

```python
BUNDLE_MAGIC = b"SEWVBND1"
BUNDLE_TRAILER = struct.calcsize("<8sQQ")   # 8s + Q + Q = 24 字节

# 读取自身 exe 最后 24 字节，校验魔数后定位 tar.xz
```

程序启动时从自己的 `sys.executable` 里读这段数据，用 `tarfile` 流式解压到 `%LOCALAPPDATA%\表格编辑器\WebView2\109.0.1518.140`，先解到 `.part` 目录再原子改名。之后每次启动直接检查缓存目录，存在就跳过解压。

这个方案有一个前提必须验证：**PyInstaller 的引导器能不能容忍 exe 尾部多出来的数据**。它的做法是从文件末尾往回找归档 cookie，理论上可行，但不能想当然。验证方法很土但有效：

1. 复制轻量版 exe；
2. 在末尾追加 1KB 随机字节；
3. 用 `--no-window` 启动，能正常跑完即说明引导器不受影响。

实测通过后才敢采用。最终通用版第一次启动需要约 9.5 秒准备内核（带等待提示框），之后普通启动 3 秒左右。

选择内置内核的条件也做了判断：Win10 及以上如果系统已装 WebView2，就直接用系统的，不浪费磁盘；只有 Win7/8 或系统缺失时才启用内置版。调试时可以设 `SHEET_EDITOR_WEBVIEW_RUNTIME=bundled` 强制走内置路径，方便验证。

### 5.4 打包机的隐形污染：WinError 193

Win7 版必须用 Python 3.8 的 32 位环境构建（pywebview 5.4 + pythonnet 3.0.3）。第一次打包后程序能启动，但一打开 xlsx 就报：

```
OSError: [WinError 193] %1 不是有效的 Win32 应用程序
```

原因不在代码：打包机用户目录里装着 64 位 Python 的 `site-packages`（里面有 numpy），openpyxl 尝试导入时拿到了 64 位 DLL，和 32 位解释器不匹配。

解决办法是在构建和运行时都设置：

```
PYTHONNOUSERSITE=1
```

彻底禁用用户级 site-packages。这类问题很难从报错本身看出来，但它提醒了一件事：**构建环境的干净程度，和代码正确性同样重要**。

### 5.5 启动速度：先减体积，再谈优化

在 1.0.2 阶段，单文件有 33.5MB，启动接近 4 秒。分析后发现两个大头：

- `tkinter` 占了 922 个小文件。窗口里的打开/保存/选文件夹对话框改用 `ctypes` 直接调 `comdlg32`、`SHBrowseForFolderW` 和 `MessageBoxW`；
- `PIL` 只是 openpyxl 的可选图片支持，实际没用到，直接排除。

spec 里补充 excludes（PIL、numpy、pandas、tcl-tk 等）后：

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| exe 体积 | 33.5MB | 11.7MB |
| 解压文件数 | 1051 | 126 |
| 首次启动 | 3.6–4.0s | 约 3.3s |
| 之后启动 | 约 4s | 1.7–2.3s |

还评估过"首次解压到缓存、以后直接运行"的启动器方案，实测只快 0.4–0.9 秒，却要引入缓存目录、杀毒误报和维护成本，放弃。

### 5.6 等待框与截图验证

首次准备内核要 9 秒，这段时间如果窗口不出现，用户会以为程序没启动。做法是在后台线程弹一个 Win32 原生 MessageBox 作为等待提示，准备完成后用 `FindWindowW("#32770", 标题)` 找到它并 `PostMessageW(WM_CLOSE)` 关掉。比自绘进度窗简单得多，也不依赖 GUI 框架。

自动化验证也遇到一个小坑：用 `PrintWindow` 抓 WebView2 窗口只能得到黑图。改成通过 `webview.settings["REMOTE_DEBUGGING_PORT"]` 打开调试端口，用 CDP 截图才拿到真实界面。这一步对确认"双击文件确实被打开、数据确实渲染出来"很关键——只看进程存活是不够的。

## 六、实测数据

| 场景 | 通用版 | 轻量版 |
| --- | --- | --- |
| 普通启动（内核已就绪） | 2.7–3.8s | 2.3–2.6s |
| 首次启动（需准备内核） | 约 9.5s | 不适用 |
| 已有窗口时双击新文件 | 2.0–2.2s | 2.0–2.2s |

验证内容：

- xlsx 与 HTML 文件通过命令行参数打开，界面数据正确；
- 第二次启动带文件参数时，新进程退出、老窗口出现新标签页；
- 内置内核路径被强制启用时，CDP 报告 `Edg/109.0.1518.140`，页面正常渲染；
- 关联的建立与取消在打包版上实际执行，测试机原默认程序（ET.Xlsx.6）正确还原，无残留 ProgID。

## 七、复现构建

```bash
# Win10+ 轻量版（Python 3.11）
pyinstaller 表格编辑器.spec

# Win7 通用版（Python 3.8 32 位）
set PYTHONNOUSERSITE=1
pyinstaller 表格编辑器-win7.spec
```

通用版构建完成后，还需要把 WebView2 109 的 `tar.xz` 追加到 exe 末尾并写入 24 字节尾针。这一步不在 PyInstaller 内部完成，属于独立的打包步骤。

## 八、经验总结

1. **先验证最危险的假设。** "PyInstaller 能否容忍尾部数据"如果不先花十分钟验证，后面所有工作都可能推倒重来。
2. **窗口程序没有 stdout。** 任何未捕获的异常、任何 `argparse` 的退出，用户看到的都只是"没反应"。入口处要把参数问题兜住，日志要落盘。
3. **平台差异要落到具体版本。** "支持 Win7"不是一句口号，它意味着 32 位 Python、固定版 WebView2、.NET Framework 4.6.2 前置、314MB 磁盘缓存。
4. **体积优化和启动优化是两件事。** 减体积（去 tkinter/PIL）收益明确；加缓存启动器收益很小，不要为了"看起来更快"增加复杂度。
5. **不要和操作系统的安全机制硬碰。** Win10 的默认应用哈希保护就是改不了，正确做法是把用户引导到系统设置，而不是研究怎么绕过。
6. **功能克制。** 多格式支持曾经让体积和复杂度一路上涨，砍掉之后启动更快、维护更简单。对工具类软件，少即是多。

## 九、1.1.0：公式、按列筛选与冻结首行

1.0.3 稳定之后，最常被提的两件事是"能不能像 WPS 一样算数"和"表头筛选项在哪"。1.1.0 补上了公式、WPS 风格的按列筛选和冻结首行，仍然保持单文件交付。

### 9.1 自己写一个公式引擎

后端没有引入任何表格计算库，公式放在前端 `static/formula.js` 里自己实现：

- 词法分析 + 递归下降解析，优先级从低到高为 `比较 < &（文本连接） < +- < */ < ^`，一元正负号比 `^` 更紧（`-2^2 = 4`，与 Excel 一致），支持后缀 `%`；
- 支持单元格引用、区域引用、`$A$1` 绝对引用，错误值用 `#DIV/0!`、`#VALUE!`、`#NAME?`、`#REF!`、`#NUM!`、`#N/A` 表示，应用层额外检测循环引用显示 `#CIRC!`；
- 内置 SUM、AVERAGE、COUNT、COUNTA、MAX/MIN、ROUND 系列、IF/IFERROR、COUNTIF/SUMIF、VLOOKUP、文本与日期函数等 40 多个，覆盖面按实际办公场景取舍。

坐标系这里踩了一个隐蔽的坑。最初按"第一条数据行是 A1"实现，后来发现从 xlsx 读进来的公式（例如 `=B2*C2`）在 Excel 里是按"表头是第 1 行、第一条数据是第 2 行"写的，两套坐标一旦混用，打开文件就会全体错位。最终统一到 Excel 坐标：引擎的第 0 行就是表头，界面行号也据此显示，从根上消除换算。

结构化编辑（插入/删除行列、删除重复行）时，公式里的引用需要跟着动。做法是对公式重新分词，只重写引用记号：保留 `$`、跳过后面紧跟 `(` 的函数名（否则 `LOG10` 会被误认成 `L10`）、被删掉的行列输出 `#REF!`。这套换算有 15 条 Node 单测覆盖。

### 9.2 公式如何落盘

- 读取 xlsx 时用 `load_workbook(..., data_only=False)`，保留公式文本而不是缓存值；
- 保存 xlsx 时，以 `=` 开头的字符串会被 openpyxl 写成公式，数字格式设为 General，Excel/WPS 打开可以继续计算；
- 前端保存时额外上传 `displayRows`（计算后的显示值），保存 HTML 表格时用它写单元格，导出的网页里看到的就是结果而不是公式。

### 9.3 WPS 风格的按列筛选

每个表头右侧有一个漏斗按钮，点开后是值清单：带出现次数、全选、关键字搜索、"（空白）"项，以及"清除该列/取消/确定"。多列筛选按 AND 叠加，和顶部"仅显示匹配行"的搜索结果取交集，状态栏显示"筛选后 N 行"。筛选状态随文件保存、进入撤销快照，切换标签页不会丢。工具栏的"清除筛选"一次取消所有列。

实现上没有偷懒用 `<select multiple>`，而是自绘浮层：固定宽度 292px，值超过 1000 个时只渲染前 1000 个并提示搜索缩小范围，避免大表卡死。

### 9.4 冻结首行

表头本来用 `position: sticky` 固定在顶部。冻结首行是把第一条可见数据行也渲染成一个 sticky 行，`top: 38px` 贴在表头下沿。难点在虚拟滚动：冻结行插入 tbody 后，后面行的自然位置整体下移了一行，所以滚动时用于占位的 spacer 高度要从 `start × 行高` 改成 `(start − 1) × 行高`，否则滚动越深、错位越大。

验证仍然走 CDP：滚动 700px 后检查表头是否仍贴顶、冻结行是否紧贴表头下沿、后续行号是否连续，并确认冻结行可以双击编辑。截图确认浅色与深色主题下都没有遮挡异常。

### 9.5 测试组合

- `tools/testenv/formula_test.js`：72 条公式引擎单测；
- `tools/testenv/remap_test.js`：15 条引用换算单测；
- Python fixture：openpyxl 造带公式的 xlsx，验证读取、保存、HTML 导出三条链路；
- `tools/testenv/cdp_ui.js`、`cdp_freeze.js`、`cdp_filter2.js`、`cdp_edit.js`、`cdp_struct.js`：用 CDP 驱动真实界面，覆盖公式显示、编辑、报错、撤销、保存、多列筛选、搜索叠加、冻结行与滚动、插入/删除行后的引用调整；

## 十、公式栏、统一编辑入口与公式自动补全

### 10.1 WPS 风格公式栏

表格上方新增 `formula-bar`：左侧名称框（显示当前引用，如 E2，输入引用回车可跳转并校验范围）、fx 分隔、内容输入框（等宽字体，显示单元格原始内容，公式显示 `=` 原文）。文件未打开时整条隐藏，随工具栏同步显隐。

### 10.2 统一编辑入口

编辑会话统一由 `state.editing` 管理：`cellInput` 是挂在单元格里的输入框，`input` 指向当前持有焦点的编辑器（单元格或公式栏），`viaBar` 标记焦点位置。两端内容实时互相同步；焦点在单元格与公式栏之间转移时保持同一会话不提交（`onEditorBlur` 按 relatedTarget 转移，公式栏 focus 事件兜底接管）。Esc 直接取消整个编辑；Enter 确认并下移；Tab 确认并右移。在网格上直接键入可打印字符即进入编辑（WPS/Excel 习惯）。

### 10.3 修复“两个编辑框”

原因：`td.active-cell` 与内部 `input.cell-input` 各画了一圈 2px 内描边，视觉上是嵌套的双框。修复：编辑时给 td 加 `editing` 类，td 统一画边框并去掉内边距，输入框改为 `width/height: 100%`、自身无边框，任何时刻只呈现一层边框。

### 10.4 公式自动补全

输入以 `=` 开头的内容时弹出 VS Code 风格候选菜单（`.ac-menu`，全局唯一实例，固定定位在编辑器下方，空间不足时上翻）：

- 按光标前的标识符 token 过滤：函数（带签名说明，常用函数优先、其余按字母序）+ 单元格引用（如输入 `A` 提示 A1…A5，表头是第 1 行、数据从第 2 行起，与公式行号一致）；
- 刚输入 `=` 时列出常用函数（SUM、AVERAGE、MAX、MIN、IF 等 15 个）；
- 方向键切换、Tab 或点击采纳（采纳函数自动补 `(`，采纳后不重弹菜单，避免循环追加）、Esc 关闭；
- Enter 不采纳候选、直接确认输入，这是和 VS Code 的关键差异——避免“打完公式回车时尾部引用被候选替换”的问题；
- 函数签名说明来自 `formula.js` 新增的 `SIGNATURES` 表（40+ 项），随 `SheetFormula.signatures` 暴露。

### 10.5 踩过的坑

- Enter 采纳候选 + 采纳后菜单重弹，两者叠加会把公式改坏（如 `=SUM(C2:D5)` 被追加成 `=SUM(C2:D5)SUM(`），靠“Enter 只确认、Tab 才采纳、采纳后不重弹”三条规则一起解决；
- programmatic `focus()` 的 `blur.relatedTarget` 可能为空，焦点转移不能只依赖 relatedTarget，公式栏 focus 事件兜底；
- Esc 在菜单可见时只关菜单不取消编辑，残留会话会被下一次 `startEdit` 的 `commitEdit()` 提交到旧单元格，出现“改一个数另一个格子变成 200”的怪象——改为 Esc 一步取消整个编辑；
- 上下键切换候选看似无效：输入框 keyup 上的 `updateAutocomplete` 会用相同 token 重建菜单并重置选中项，token 未变化且菜单已开时直接保留选中即可；
- CEF 下脚本调用 `focus()` 偶发不派发 focus 事件，编辑会话的 viaBar 方向改由 `syncFocusState()`（在 keydown/input/补全入口按 `document.activeElement` 自愈）兜底。

## 十一、Ctrl+Enter、公式引用高亮与区域角标

### 11.1 Ctrl+Enter 直接提交

编辑器（单元格与公式栏通用）按 Ctrl+Enter 直接提交当前内容且光标留在原单元格，与 Enter（提交并下移）区分；帮助弹窗已补充说明。

### 11.2 编辑公式时点击插入引用

编辑以 `=` 开头的内容时，点击其他单元格把引用插入光标处（不再切换选中）；光标夹在参数中间时自动补逗号，保证公式始终有效；Shift+点击第二个单元格插入区域（如 `C3:C4`）。实现上拦截了 `mousedown` 默认行为防止输入框失焦被提交，公式编辑之外的点击行为完全不变。

### 11.3 引用高亮与区域角标

`formula.js` 新增 `parseRefs`（token 带文本位置），`app.js` 编辑公式时解析出全部引用并绘制固定定位高亮层：每个引用一个彩色框（光标所在引用用强调底色，其余描边），范围引用右下角带圆形角标；角标点击弹出小窗，可改写或删除该引用（写回公式原位置）。高亮随输入、光标移动、滚动、渲染即时重算；引用指向表头行或虚拟滚动可视区外时跳过不绘。行列增删引发的引用换算仍由原有 `remapRefs` 链路负责。

### 11.4 编辑期间滚动

虚拟滚动会重建 tbody 吞掉编辑框，现在滚动时先把编辑中的内容提交（与失焦提交语义一致），避免编辑器“凭空消失”。
